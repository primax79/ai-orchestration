# 12.1 Dati sulla ripresa headless (dal vivo, 2026-10-18)

Osservato con le vere CLI tramite il motore di esecuzione (`ai-orch run start --continue`), in un repository git temporaneo sotto `.tmp/` del worktree di 07.5. Versioni: claude 2.1.296 (modello haiku), kilo 7.8.8 (modello `google/gemini-3.8-flash`), codex-cli 0.147.0 (modello `gpt-5.6-luna`, login ChatGPT). Ogni ripresa avviene in un nuovo processo del sistema operativo, quindi ogni riga è anche una "ripresa da un processo nuovo". Flussi grezzi: `scripts/fixtures/runs/` (ripuliti).

"Controllo di memoria" significa che al turno ripreso è stato chiesto, senza l'uso di tool, cosa fosse accaduto in precedenza nella sessione, ottenendo una risposta corretta.

## Utilizzo normalizzato (specifica §0c E8)

Implementato in `usage_from_objects` (`scripts/orchestration_runs.py`), memorizzato per ciascuna esecuzione in `run.json` `usage`:

| Campo | Kilo (`step_finish.part`) | Claude (`result`) | Codex (`turn.completed`) |
| --- | --- | --- | --- |
| `input_tokens` (non in cache) | Σ `tokens.input` | `usage.input_tokens` | Δ(`input_tokens` − `cached_input_tokens`) |
| `cache_read` | Σ `tokens.cache.read` | `usage.cache_read_input_tokens` | Δ `cached_input_tokens` |
| `cache_write` | Σ `tokens.cache.write` | `usage.cache_creation_input_tokens` | Δ `cache_write_input_tokens` (0 finora) |
| `output_tokens` | Σ (`tokens.output` + `tokens.reasoning`) | `usage.output_tokens` | Δ `output_tokens` |
| `estimated_context_tokens` | `tokens.total` dell'ultimo passo | ultimo di `usage.iterations` (input + cache read + cache write + output) | rollout `token_count.info.last_token_usage` (best effort; None se non trovato) |
| `cost_usd` | Σ `part.cost` | `total_cost_usd` | non riportato (None) |

**L'utilizzo di Codex è cumulativo sull'intero thread, non per singolo turno** (un turno ripreso di una sola riga ha riportato 120.663 token di input dopo un primo turno di 104.655; il `total_token_usage` del rollout corrisponde al flusso). Δ è la differenza rispetto all'esecuzione precedente più vicina nella catena di continuazione che abbia registrato `usage.session_totals`. La rotazione (E8) deve usare `estimated_context_tokens`, mai queste somme.

Dimensioni osservate: un turno execute banale di Kilo è terminato a ~38k token di contesto, uno di Claude haiku a ~65k (system prompt e tool propri di Claude Code), uno di Codex a ~16k.

## Correzioni al motore effettuate in 07.5 (locali ai parser e ai controlli di continuazione)

- `session-busy`: `run start --continue` rifiuta mentre un'altra esecuzione attiva dello stesso tool detiene il medesimo `session_id` (specifica §0 "never two resumptions of the same session at the same time").
- Mancata corrispondenza della sessione: quando il flusso di una continuazione riporta un altro id di sessione, l'esecuzione viene segnata `failed` con `session_mismatch: true`, `observed_session_id` e un `invariant_error` (intercetta il fallback sul nome di Codex; il caso non-UUID di Claude termina già con codice 1).
- `agent_error` registrato sulle esecuzioni fallite (evento di errore del flusso, altrimenti l'ultima riga di stderr), così 12.5 può classificare "session not found" senza leggere i log.
- Argv di ripresa di Kilo: `--` prima del messaggio (falliva con `File not found: Continue.`).

## Follow-up sul motore non svolti qui (non locali ai parser)

1. **L'annullamento lascia in esecuzione i processi dei tool di Kilo.** La terminazione del gruppo di processi non colpisce i processi figli che Kilo avvia in un gruppo proprio (`sleep 45` è sopravvissuto a `run cancel`, riassegnato al pid 1). Terminare l'albero dei discendenti dell'agente (attraversando per ppid prima di inviare il segnale) oppure eseguire l'agente sotto una sessione dedicata e terminare per id di sessione.
2. **Continuare un'esecuzione di verifica, o qualsiasi esecuzione il cui worktree sia stato rimosso, gira in una directory vuota.** Il supervisore esegue `mkdir` su una `cwd` mancante; per un'esecuzione di verifica il worktree usa e getta viene rimosso dopo il completamento. Rifiutare invece la continuazione (o ricreare il worktree a `target_commit`).
3. **Un'esecuzione di verifica rimuove `worktree_path` al completamento anche quando quel percorso è il worktree execute di un'altra esecuzione** (osservato con un record di verifica costruito a mano che aveva ereditato il worktree di un'esecuzione execute): limitare la rimozione ai soli worktree creati dall'esecuzione di verifica.
4. **La transizione del file del task rende sporco il repository target.** Quando `tasks/` risiede nel repository target, la transizione a `in progress` scritta dal supervisore lascia il repository sporco, perciò un secondo `execute` nello stesso repository viene rifiutato (`dirty-repo`) finché qualcuno non committa il file del task. Ignorare `tasks/` nel controllo di pulizia oppure committare la transizione.
5. **Un `execute` fallito lascia il task `in progress`** senza modo di tornare a `open` (`in progress -> open` non è consentito); un nuovo tentativo richiede un nuovo task o una modifica manuale.
6. **La ripresa di Kilo richiede il progetto originale.** Riprendere in un altro repository fallisce con un errore opaco del server; il ruolo di orchestratore (12.5) deve mantenere i propri turni in un'unica directory di progetto e trattare questo errore come "session not found".
7. **I valori predefiniti dei profili raggiungono silenziosamente modelli costosi.** Un `verify` senza `--profile` si risolve in `deep-reasoning`, e quando nel file configurato manca quel profilo vengono applicati i valori predefiniti integrati (`opus`/`high`, `google/gemini-4-argon`/`high`). Vale la pena aggiungere un avviso nell'anteprima quando il modello proviene dai valori predefiniti integrati.
