## Behaviour checks

- `initialize` answered by the shim before the broker exists: yes (all three clients connect).
- Two shims at once → one broker: covered by the spike's tests (`backend/test_broker.py`, 7 passed).
- Broker killed mid-session → the next call relaunches it and succeeds (pid 24012 → 47234, a single broker process).
- **Result size:** `tasks_list` on `ai-orchestration` (≈1 MB JSON) fails in the shim's HTTP relay
  (`unhandled errors in a TaskGroup`); 140 KB works. Not investigated further: the real tools must return compact,
  paged results anyway (a megabyte in a model's context is useless).

## Amendments to carry into the spec and 16.5

1. The broker serialises MCP results without nulls (`exclude_none`), at the source rather than in the shim.
2. The Doctor/setup MCP registration for Codex writes `default_tools_approval_mode` explicitly: `approve` for read
   tools is safe; for write tools prefer per-tool approval or `writes` if supported (to be verified when write tools
   exist), never a global bypass.
3. Read tools are compact and paged (`tasks.list` returns id, short title, state, priority, project; details via
   `tasks.show`), with a hard response cap and a clear "truncated, use cursor" marker.
4. Field naming is part of the contract (`whoami` returned `pid` where the prompt expected `broker_pid`): fix the names
   in the spec's tool list before 16.5.
5. Kilo-run processes again hung after finishing (both the 16.1 and an earlier T025 run): `server-and-bindings` T012 of
   `ai-orchestration` remains relevant for anything that drives `kilo run`, including future broker-hosted Kilo turns.
